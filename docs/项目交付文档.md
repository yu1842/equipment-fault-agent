## 文档说明

本文档对应一个**可运行、可复现**的最小 Agent 项目：用户在 Windows 客户端中用自然语言描述设备故障，Agent 自主调用本地检索工具查询模拟案例库，并依据检索结果给出可能原因与处理步骤；对知识库未覆盖的问题明确说明"缺乏依据"，不编造案例。

全文分为四部分：

- **第一部分 项目全流程**：六个阶段的关键节点、交付物、时间节点与验收标准，可直接用作项目管理基线。
- **第二部分 系统架构**：技术栈选型、分层设计、模块划分、接口规范、数据流向与非功能性设计，兼顾当下可落地与后续可扩展。
- **第三部分 MVP 方案**：把范围收敛到"最小成本跑通核心业务闭环"，给出功能边界、优先级、验证指标与退出条件。
- **第四部分 交付物与验收**：Windows 客户端的功能说明、运行方式与验收清单。

# 第一部分 项目全流程

## 1.1 项目概述

### 1.1.1 背景

制造企业设备运维高度依赖老师傅经验：故障描述口径不一、案例散落在个人笔记与工单系统、新人上手周期长。大模型具备语言理解能力，但直接问答存在两个硬伤——**会编造不存在的案例**、**无法追溯依据**。本项目以"**检索先行、依据可查**"为核心思路，用最小成本验证一个判断：

> 在只有十几条结构化案例的条件下，"Agent 自主调用检索工具 + 依据检索结果作答 + 无依据时明确拒答"这一交互范式，是否已经能支撑一线维修人员的初步排查？

### 1.1.2 项目目标

| 层级 | 目标 | 可衡量结果 |
|---|---|---|
| 业务目标 | 让维修人员在 30 秒内获得有依据的排查方向 | 单次问答 ≤ 5 秒（离线 ≤ 50 ms），回答必须带案例编号 |
| 技术目标 | 零第三方依赖、可在任意 Windows 机器上启动 | 安装包体积为 0，`python app.py` 直接运行，无 pip 安装 |
| 过程目标 | 完整走通"需求→设计→开发→测试→部署→迭代" | 六阶段交付物齐备，89 个自动化测试全部通过 |
| 学习目标 | 能独立解释 Agent 工作流、工具调用与调试过程 | 可现场演示工具调用记录并解释每条参数与返回值 |

### 1.1.3 项目范围

**范围内**：本地模拟知识库检索、工具调用编排、回答生成、异常处理、Windows 桌面客户端、日志与可追溯记录。

**范围外**（明确不做，避免范围蔓延）：真实设备接入（PLC / OPC-UA / Modbus）、设备控制指令下发、案例库在线协同编辑、多租户权限体系、移动端。

### 1.1.4 成功标准（Definition of Success）

1. 三条核心用例全部通过：正常故障、未覆盖故障、异常输入。
2. 每次回答都能在界面上看到对应的工具调用记录（工具名、参数、返回值摘要、耗时）。
3. 拔掉网络、清空密钥后，程序仍能完整演示检索闭环，且明确标注"离线规则模式"。
4. 新机器上双击 `start.bat` 即可启动，无需安装任何依赖。

## 1.2 阶段模型与里程碑

项目采用**六阶段瀑布 + 迭代回归**的混合模型：主流程按阶段推进保证交付确定性，测试与迭代阶段允许回流到开发阶段做小步修正。

| 里程碑 | 名称 | 判定标志 |
|---|---|---|
| M1 | 需求基线确认 | 需求清单与范围外清单签字确认，验收标准可测 |
| M2 | 设计基线确认 | 架构图、模块清单、接口契约冻结 |
| M3 | 核心链路打通 | `--cli` 模式可完成一次完整的"检索→回答"闭环 |
| M4 | 测试通过 | 自动化测试全绿，三条核心用例手工验证通过 |
| M5 | 部署可用 | 目标机器双击启动成功，日志正常落盘 |
| M6 | 迭代基线 | 遗留问题清单与下一迭代计划确认 |

## 1.3 阶段一：需求分析

**阶段目标**：把"做一个设备故障 Agent"的模糊诉求，转成可开发、可验收的需求条目。

**关键活动**

1. 角色访谈：明确唯一主角色是"设备维修工"，次角色是"设备主管"（只看结论）。
2. 场景枚举：收集 12 类典型设备故障描述，提炼字段结构（设备、现象、原因、步骤、风险）。
3. 能力拆解：把"会回答问题"拆成"能检索、能判断要不要检索、能基于依据作答、无依据要拒答"。
4. 边界确认：明确只读模拟库、不做设备控制，形成安全约束条款。
5. 验收标准编写：每条需求必须能用一个可执行的测试用例验证。

**关键节点**

| 节点 | 内容 | 完成标志 |
|---|---|---|
| N1.1 | 角色与场景确认 | 输出 3 个主场景描述 |
| N1.2 | 功能清单确认 | F1~F10 共 10 条功能，标注 Must/Should |
| N1.3 | 非功能需求确认 | 性能、兼容性、安全三类指标量化 |
| N1.4 | 需求基线评审 | M1 通过，需求变更需走变更单 |

**交付物**

- 《需求规格说明》（功能清单 F1~F10、非功能指标、范围外清单）
- 故障案例字段定义表与 12 条模拟数据初稿
- 验收标准清单（对应测试用例编号）

**时间节点**：0.5 人日（作业节奏下约 40 分钟）。

**验收标准**

1. 每条功能需求都有唯一编号、优先级与验收方式，无"体验良好"这类不可测描述。
2. 范围外清单明确列出至少 3 项，防止后续被追加。
3. 模拟案例条数 ≥ 5，且字段完整率 100%（编号/设备/现象/原因/步骤齐备）。
4. 安全约束（只读、不控设备、不泄露密钥）写入需求正文而非附录。

## 1.4 阶段二：设计

**阶段目标**：把需求翻译成"能写代码"的结构，重点是分层、模块边界与接口契约。

**关键活动**

1. 架构选型：确定单机分层架构（表现层/应用层/领域层/数据层），放弃引入 Web 框架。
2. 技术选型：GUI 用 Tkinter、HTTP 用 urllib、数据用 JSON，确保零第三方依赖。
3. 模块划分：按"配置、知识、工具、模型、编排、日志、界面"七块切分，明确依赖方向单向向下。
4. 接口设计：定义工具的 JSON Schema 契约与统一返回结构 `{ok, ...}`（3 个业务工具 + 3 个工程知识工具）。
5. 异常设计：列出 7 类失败路径（空输入、库缺失、库损坏、缺密钥、鉴权失败、超时、轮次超限）及各自降级策略。
6. 界面设计：单窗口三区布局（对话区、信息区、状态栏），确认信息密度与操作路径。

**关键节点**

| 节点 | 内容 | 完成标志 |
|---|---|---|
| N2.1 | 架构图与分层确认 | 四层职责边界清晰，无跨层调用 |
| N2.2 | 模块清单确认 | 7 个模块，依赖方向单一 |
| N2.3 | 接口契约冻结 | 工具 Schema 与返回结构定稿 |
| N2.4 | 异常矩阵确认 | 7 类异常均有确定的用户可见提示 |
| N2.5 | 设计评审 | M2 通过 |

**交付物**

- 系统架构图（分层 + 数据流）
- 模块清单与目录结构说明
- 接口规范（工具 Schema、模型请求/响应、错误码表）
- 数据字典（案例字段定义）
- 界面布局稿与交互说明

**时间节点**：0.5 人日（作业节奏下约 30~40 分钟，与阶段一交错进行）。

**验收标准**

1. 每个模块职责可用一句话说清，且不存在两个模块职责重叠。
2. 接口契约包含必填字段、类型、取值范围与失败返回。
3. 每个异常都能映射到"用户看到什么 + 系统记录什么"。
4. 架构方案能回答"要加第 4 个工具，需要改哪些文件"这类扩展性问题（答案：只改 `tools.py` 与提示词）。

## 1.5 阶段三：开发

**阶段目标**：以最小可运行单元推进，先打通链路，再补齐体验。

**关键活动**

1. 骨架搭建：目录、`pyproject.toml`、`.gitignore`、`app.py` 入口（GUI / CLI / 自检三模式）。
2. 数据先行：先落首批 12 条案例，保证检索有东西可查（v2.2 已扩至 24 条）。
3. 检索实现：加权打分 + 二元组相似度，输出可解释的分数。
4. 工具层实现：注册表、参数校验、异常兜底、调用记录四件事一次做完。
5. 模型层实现：OpenAI 兼容客户端，处理 HTTP 错误、超时、非 JSON 响应。
6. 编排层实现：在线 tool-calling 循环（最多 6 轮）+ 离线规则兜底 + 历史裁剪。
7. 界面实现：Tkinter 三区布局、后台线程 + 队列刷新、工具面板、知识库浏览、设置对话框。
8. 日志实现：JSONL 逐条落盘，作为"真实工具调用"的证据链。

**关键节点**

| 节点 | 内容 | 完成标志 |
|---|---|---|
| N3.1 | 骨架可运行 | `--list` 能列出设备类型（当前 19 类） |
| N3.2 | 检索可用 | 液压站问题命中 EFA-001，分数 > 0.4 |
| N3.3 | 工具层可用 | 4 类失败路径均返回结构化错误 |
| N3.4 | 闭环打通（M3） | `--cli` 输出四段式回答 + 工具调用列表 |
| N3.5 | 界面可用 | 窗口正常显示，提问后工具面板出现记录 |
| N3.6 | 代码审查 | 关键函数逐行可解释，无魔数、无硬编码密钥 |

**交付物**

- 可运行源码（`app.py`、`src/efa/*`、`data/fault_cases.json`）
- `pyproject.toml`、`start.bat`、`config.example.json`
- 开发记录（问题 → 定位 → 修复 → 验证）
- 至少 3 次有意义的 Git 提交

**时间节点**：1.5 人日（作业节奏下约 100 分钟）。

**验收标准**

1. `python app.py --cli "液压站压力上不去"` 能返回包含 EFA-001 的完整回答，并列出 2 次工具调用。
2. 无 API Key 时程序不崩溃、不静默失败，而是明确进入离线模式。
3. 代码中不存在硬编码密钥；`config.json` 已被 `.gitignore` 忽略。
4. 任一函数被问"这行在做什么"时能当场解释，不存在"AI 生成但没人懂"的黑盒代码。

## 1.6 阶段四：测试

**阶段目标**：用可重复的手段证明"该对的对了、该错的错了"。

**关键活动**

1. 单元测试：知识库加载、检索排序、文本工具函数。
2. 工具测试：参数合法性、未知工具、非法 JSON、越界 top_k。
3. 编排测试：正常问答、未覆盖拒答、空输入、知识库缺失、历史裁剪、模型不可用降级。
4. 界面测试：窗口构建、控件尺寸、回答渲染、清空重置。
5. 手工验收：三条核心用例现场演示，观察工具记录与耗时。
6. 缺陷修复：按"现象→定位→修复→复测"闭环，全部写入开发记录。

**关键节点**

| 节点 | 内容 | 完成标志 |
|---|---|---|
| N4.1 | 测试用例设计 | 覆盖正常/边界/异常三类 |
| N4.2 | 自动化测试全绿 | 89 个用例通过，无警告噪声（M4） |
| N4.3 | 手工用例验证 | 正常、未覆盖、异常输入三条全过 |
| N4.4 | 缺陷回归 | 已修缺陷 100% 复测通过 |

**交付物**

- `tests/` 下 4 个测试模块 + `run_tests.py`
- 测试执行记录（命令、输出、结论）
- 缺陷清单与修复记录

**时间节点**：1 人日（作业节奏下约 60 分钟）。

**验收标准**

1. `python run_tests.py` 输出 `Ran 89 tests ... OK`，且无异常噪声。
2. 关键业务规则有测试锁定：未覆盖必须拒答、离线必须标注模式、空输入必须友好提示。
3. 界面在 1180×760 默认尺寸下无控件重叠、无零高度控件。
4. 每个已修缺陷都有对应的回归用例或验证命令。

## 1.7 阶段五：上线部署

6. 归档与版本标记：Git 提交 + 标签 `v1.0.0`，仓库 README 首屏给出启动命令。

**关键节点**

**交付物**

**时间节点**：0.5 人日（作业节奏下约 40 分钟）。

**验收标准**

## 1.8 阶段六：迭代维护

**阶段目标**：把一次性交付变成可持续演进的产品基线。

**关键活动**

1. 反馈收集：记录"无依据"提问，作为知识库扩充的输入。
2. 指标监控：离线命中率、无依据率、平均响应时间、降级触发次数。
3. 知识库运营：新增案例、补充同义词、调整打分权重与阈值。
4. 缺陷修复：按影响面分级（阻塞/严重/一般/建议）。
5. 版本规划：每迭代只做 1~2 个主题，避免并行改动。

**关键节点**

| 节点 | 内容 | 完成标志 |
|---|---|---|
| N6.1 | 迭代计划确认 | 明确本迭代目标与不做的事 |
| N6.2 | 变更实施 | 代码 + 测试 + 文档同步更新 |
| N6.3 | 回归验证 | 全量测试通过，核心用例复测 |
| N6.4 | 版本发布 | 打 tag，更新 CHANGELOG |

**交付物**

- 迭代计划与变更记录（CHANGELOG）
- 指标看板（可从日志统计）
- 知识库更新清单

**时间节点**：每 2 周一个迭代（作业节奏下为交付后持续维护）。

**验收标准**

1. 每次变更都有对应的测试用例，不允许"只改代码不补测试"。

3. 遗留问题有明确责任人与计划时间，不允许悬空。

## 1.12 质量门禁（DoD）

一个工作项只有同时满足以下条件才算"完成"：

1. 代码通过编译检查与全部自动化测试。
2. 新增行为有对应测试用例，或说明为何无法自动化。
3. 异常路径有用户可见提示，不出现裸栈。
4. 文档（README / 开发记录）同步更新。
5. 无硬编码密钥、无调试残留、无 `__pycache__` 入库。

# 第二部分 系统架构方案

## 2.1 架构目标与约束

| 类型 | 内容 | 对架构的约束 |
|---|---|---|
| 业务约束 | 只做咨询建议，不接设备 | 不引入设备通信协议栈，架构止步于数据层 |

| 演示约束 | 无网络、无密钥也要能演示 | 必须有离线执行路径，且与在线路径共用工具与数据 |

| 演进约束 | 后续要能换模型、换知识库 | 模型层与检索层需可替换（依赖倒置） |

## 2.2 技术栈选型

| 层次 | 选型 | 版本要求 | 选型理由 | 备选方案与放弃原因 |
|---|---|---|---|---|
| 语言 | Python | ≥ 3.10 | 生态成熟、语法简洁、类型标注完备 | Node/Java：部署成本高，与本项目规模不匹配 |
| GUI | Tkinter / ttk | 随 Python 附带 | 零安装、跨 Windows 版本稳定、可打包 | PyQt：体积大、许可证复杂；Electron：需 Node 运行时 |
| HTTP | `urllib.request` | 标准库 | 只需一次 POST，无需连接池与重试框架 | `requests`：引入第三方依赖；`openai` SDK：引入传递依赖 |
| 模型接口 | OpenAI 兼容 `/chat/completions` | - | 兼容 DeepSeek/通义/智谱/本地 vLLM，换供应商只改配置 | 各厂商私有 SDK：绑定单一供应商 |
| 工具协议 | Function Calling（JSON Schema） | - | 模型原生支持，工具声明即文档 | 自研 ReAct 文本解析：鲁棒性差，易解析失败 |
| 数据 | JSON 文件 | - | 可读、可 diff、可手工维护 | SQLite：当前规模无必要；向量库：过度设计 |
| 配置 | 环境变量 + JSON | - | 密钥不落盘优先，允许本地覆盖 | 纯硬编码：不可运维 |
| 日志 | JSONL | - | 一行一条、易追加、易用脚本统计 | 文本日志：结构化查询困难 |
| 测试 | `unittest` | 标准库 | 零依赖，可被 CI 直接调用 | pytest：需额外安装 |
| 版本管理 | Git + Gitee | - | 提交历史即开发证据链 | - |

## 2.3 分层架构

系统采用**四层 + 一组横切能力**的单机分层架构，依赖方向严格自上而下，禁止反向引用。

| 层次 | 职责 | 组成 | 允许依赖 |
|---|---|---|---|
| 表现层（Presentation） | 接收输入、渲染结果、展示工具调用与知识库 | `ui/main_window.py`、`app.py`（CLI） | 应用层 |
| 应用层（Application） | 编排一次问答的生命周期：校验 → 决策 → 调用工具 → 组装回答 → 记录 | `agent.py`、`session.py` | 领域层、基础设施层 |
| 领域层（Domain） | 业务规则：检索打分、工具语义、答案结构约束 | `knowledge.py`、`tools.py` | 无（纯逻辑，可单测） |
| 基础设施层（Infrastructure） | 外部交互：模型 HTTP 调用、配置读取、文件读写 | `llm.py`、`config.py` | 标准库 |
| 横切能力 | 配置、日志、异常映射 | `config.py`、`session.py`、各模块异常类 | 全层可用 |

**关键设计决策**

1. **领域层不感知 IO**：`knowledge.py` 只接收文件路径，`tools.py` 只接收知识库对象，因此可以脱离网络与界面单独测试（89 个测试中 84 个不需要 GUI）。
2. **在线/离线同构**：两条路径都通过 `ToolRegistry.execute()` 调用工具，保证"离线演示"看到的就是真实检索结果，而非伪造文本。
3. **界面不持有业务逻辑**：`main_window.py` 只做"取输入 → 起线程 → 渲染 Answer"，所有判断在 `agent.py` 内完成，便于以后替换成 Web 前端。
4. **降级不静默**：任何降级都会在 `Answer.error` 与界面 meta 行中体现（"已自动降级"），避免把兜底结果伪装成模型输出。

## 2.4 模块划分

| 模块 | 文件 | 核心类/函数 | 职责 | 对外接口 | 依赖 |
|---|---|---|---|---|---|
| 配置 | `config.py` | `Settings` | 三级配置合并（环境变量 > config.json > 默认值）、密钥掩码、模式判定 | `Settings.load()`、`save()`、`online_ready` | 标准库 |
| 知识库 | `knowledge.py` | `KnowledgeBase`、`FaultCase`、`SearchHit` | 加载 JSON、字段校验、加权检索、按编号查询 | `search()`、`get()`、`equipment_names()` | 标准库 |
| 工具层 | `tools.py` | `ToolRegistry`、`ToolCallRecord` | 工具声明（Schema）、参数校验、执行、异常兜底、耗时记录 | `specs()`、`execute()` | `knowledge` |
| 模型层 | `llm.py` | `LLMClient`、`LLMError` | OpenAI 兼容请求、HTTP 错误分类、超时控制 | `chat(messages, tools)` | `config` |
| 编排层 | `agent.py` | `Agent`、`Answer` | 生命周期编排、tool-calling 循环、离线兜底、历史裁剪、引用提取 | `ask()`、`reset()` | `llm`、`tools`、`config` |

## 2.5 关键流程

### 2.5.1 在线模式（模型自主调用工具）

| 步骤 | 参与方 | 动作 | 失败处理 |
|---|---|---|---|
| 1 | 界面 | 校验非空 → 追加用户气泡 → 起后台线程 | 空输入：提示补充描述，不发起请求 |
| 2 | Agent | 检查知识库可用性 | 不可用：返回 `kb_unavailable` 与原因 |
| 3 | Agent | 组装 messages（system + 最近 12 条历史 + 本轮问题）与 tools 声明 | - |
| 4 | LLM | 返回 `tool_calls`（通常为 `search_fault_cases`） | 鉴权/网络/超时：捕获为 `LLMError` |
| 5 | Agent → Tools | 逐个执行工具，记录参数、返回值摘要、耗时 | 参数非法/目标不存在：转结构化错误回填模型 |
| 6 | Agent | 把工具结果以 `role=tool` 回填，进入下一轮（上限 6 轮） | 超限：抛错并降级 |
| 7 | LLM | 输出四段式自然语言回答 | 空回答：抛错并降级 |
| 8 | 界面 | 渲染回答 + meta（模式/工具次数/耗时/引用编号） | - |
| 9 | SessionLog | 落盘问题、回答、每次工具调用 | 写失败静默降级，不影响主流程 |

### 2.5.2 离线降级流程

| 步骤 | 动作 | 说明 |
|---|---|---|
| 1 | 判定降级条件 | 无密钥 / 强制离线 / `LLMError` |
| 2 | 直接调用 `search_fault_cases` | 与在线模式同一个工具实现，结果一致 |
| 3 | 有命中 → 读 `get_case_detail` 取 Top1 | 只取 Top1 详情，避免答案冗长 |
| 4 | 按模板组织四段式回答 | 首行标注"离线规则模式" |
| 5 | 无命中 → 输出"暂无案例依据" + 已覆盖设备清单 | 明确拒答，不编造 |
| 6 | 记录 `error=llm_failed: <原因>` | 界面 meta 显示"已自动降级" |

## 2.6 接口规范

### 2.6.1 工具接口（OpenAI Function Calling Schema）

**工具一：`search_fault_cases`**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `query` | string | 是 | 检索用故障描述，建议"设备名 + 现象" |
| `top_k` | integer | 否 | 返回条数，默认 3，取值 1~5，越界自动收敛 |

返回结构：

```json
{
  "ok": true,
  "query": "液压站压力上不去",
  "total_in_kb": 12,
  "hit_count": 2,
  "coverage": "有依据",
  "hits": [
    {"rank": 1, "case_id": "EFA-001", "equipment": "液压站",
     "symptom": "系统压力上不去……", "risk": "中",
     "score": 0.701, "matched_terms": ["液压站", "压力上不去"]}
  ],
  "notice": ""
}
```

**工具二：`get_case_detail`**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `case_id` | string | 是 | 案例编号，如 `EFA-001`，大小写不敏感 |

返回：`{"ok": true, "case": {编号、设备、型号、现象、原因数组、步骤数组、关键词、风险、来源}}`。

**工具三：`list_equipment`**

无入参，返回 `{"ok": true, "count": 12, "equipment": ["液压站", ...]}`，用于判断问题是否在覆盖范围内。

### 2.6.2 统一返回与错误约定

| 约定 | 内容 |
|---|---|
| 成功 | `{"ok": true, ...业务字段}` |
| 失败 | `{"ok": false, "error": "可直接展示的中文原因"}` |
| 原则 | 工具不抛异常给上层；参数错误不导致 Agent 中断；失败信息要能让模型自行纠正（例如"案例编号不存在"） |

**错误码（内部语义）**

| 标识 | 触发条件 | 用户可见表现 |
|---|---|---|
| `empty_input` | 输入为空或仅空白 | "请输入需要咨询的设备故障描述……" |
| `kb_unavailable` | 知识库文件缺失/损坏/为空 | "知识库未能加载，原因：……" |
| `llm_failed` | 鉴权失败、超时、断网、空回答、轮次超限 | 自动降级 + "已自动切换为本地规则模式" |
| `tool_error` | 工具参数非法或目标不存在 | 回填给模型，由模型修正后重试 |

### 2.6.3 模型接口

请求：`POST {base_url}/chat/completions`，`Authorization: Bearer <key>`，`Content-Type: application/json`。

```json
{
  "model": "deepseek-chat",
  "messages": [{"role": "system", "content": "..."}, {"role": "user", "content": "..."}],
  "tools": [{"type": "function", "function": {"name": "search_fault_cases", "...": "..."}}],
  "tool_choice": "auto",
  "temperature": 0.2,
  "stream": false
}
```

响应处理：取 `choices[0].message`；若含 `tool_calls` 则进入下一轮，否则取 `content` 作为最终回答；`usage` 用于 token 统计。

## 2.7 数据流向与数据模型

### 2.7.1 数据流

| 环节 | 输入 | 处理 | 输出 |
|---|---|---|---|
| 采集 | 用户自然语言 | 去空白、长度校验 | 规范化问题串 |
| 检索 | 问题串 | 归一化 → 二元组 → 加权打分 → 阈值过滤 → 排序 | Top-K 命中（含分数与命中词） |
| 增强 | Top1 编号 | 读取完整案例 | 原因数组、步骤数组、风险等级 |
| 生成 | 命中结果 / 模型上下文 | 在线：模型组织；离线：模板组织 | 四段式回答 |
| 呈现 | 回答 + 工具记录 | 渲染气泡、meta、工具面板 | 用户可见结果 |
| 留痕 | 全过程 | JSONL 逐条追加 | `logs/session-*.jsonl` |

### 2.7.2 数据字典（案例字段）

| 字段 | 类型 | 必填 | 约束 | 示例 |
|---|---|---|---|---|
| `id` | string | 是 | `EFA-` + 三位序号，全局唯一 | `EFA-001` |
| `equipment` | string | 是 | 设备类型名，用于设备命中加权 | `液压站` |
| `model` | string | 是 | 型号或适用范围 | `YZ-63 系列` |
| `symptom` | string | 是 | 一句话描述现象，用于相似度计算 | `系统压力上不去……` |
| `causes` | string[] | 是 | ≥1 条，按可能性降序 | `液压油量不足……` |
| `steps` | string[] | 是 | ≥1 条，安全措施必须在前 | `停机并执行能量隔离……` |
| `keywords` | string[] | 是 | ≥3 个，含口语化说法 | `压力上不去`、`无力` |
| `risk` | string | 是 | 高/中/低 | `中` |
| `source` | string | 否 | 数据来源说明 | `模拟案例（依据……编写）` |

### 2.7.3 检索算法

```
输入：query, top_k, min_score
输出：按 score 降序的 SearchHit 列表

对每个案例 case：
    score  = 0.42 * (设备名出现在 query 中)
    score += 0.20 * min(关键词命中数, 4)
    score += 0.55 * dice(bigrams(query), bigrams(case.symptom))
    score += 0.20 * dice(bigrams(query), bigrams(case.全文))
    score  = 1 - exp(-1.15 * score)          # 单调压缩至 0~1
    若 score >= min_score 则入候选

候选按 (-score, id) 排序，取前 top_k 条
```

**设计意图**：设备名与关键词保证精确命中，Dice 相似度兜住"同一故障的不同说法"，指数压缩避免多关键词线性叠加越界。阈值 `min_score=0.22` 是"有依据 / 无依据"的分界线，可通过配置调整并在测试中锁定行为。

## 2.8 非功能性设计

### 2.8.1 性能

| 指标 | 目标 | 实测/实现手段 |
|---|---|---|
| 冷启动 | ≤ 2 s | 仅导入标准库；界面构建与知识库加载同步完成（24 条案例 < 10 ms） |
| 离线单轮响应 | ≤ 50 ms | 纯内存计算，实测 0~5 ms |
| 在线单轮响应 | 取决于模型，超时 60 s 可配 | 后台线程 + 队列刷新，界面不阻塞；超时即降级 |
| 内存占用 | < 60 MB | 无缓存膨胀，历史仅保留最近 12 条消息 |
| 检索复杂度 | O(案例数 × 词表) | 百条量级无压力；千条以上需换倒排索引或向量检索 |

### 2.8.2 安全

| 威胁 | 对策 |
|---|---|
| 密钥泄露 | 环境变量优先；`config.json` 入 `.gitignore`；界面掩码显示；日志不写密钥 |
| 误操作真实设备 | 架构上不引入设备通信能力；提示词禁止输出控制指令；界面与关于页声明边界 |
| 模型编造案例 | 检索为空即拒答；回答必须带案例编号；单元测试锁定"未覆盖必拒答" |
| 提示词注入 | 系统提示词置于最前并声明规则；工具只读、无副作用，注入最多导致无效检索 |
| 恶意参数 | 工具层校验类型与范围（`top_k` 收敛 1~5），非法 JSON 转结构化错误 |
| 数据污染 | 知识库为只读模拟数据，无用户写入通道 |

### 2.8.3 可扩展性

| 扩展方向 | 改动点 | 是否需要改架构 |
|---|---|---|
| 新增工具 | `tools.py` 增加实现 + Schema | 否 |
| 更换模型供应商 | `config.json` 改 `base_url` / `model` | 否 |
| 知识库扩容至千条 | `knowledge.py` 换倒排索引或向量检索 | 否（接口不变） |
| 增加 Web 前端 | 新增表现层，复用 `Agent.ask()` | 否 |
| 多轮追问与工单生成 | 编排层增加状态与导出工具 | 否 |
| 多用户/权限 | 需引入服务化与认证 | 是，属于下一阶段 |

### 2.8.4 可维护性

1. **单一职责**：每个模块可用一句话概括，无"万能工具类"。
2. **依赖单向**：界面 → 编排 → 领域/基础设施，反向依赖为 0。
3. **可测试**：领域层无 IO，24 个测试无需 GUI 即可运行。
4. **可观测**：每次问答都有 JSONL 记录，含工具参数、返回摘要、耗时、异常。
5. **可配置**：模型、地址、超时、轮次、Top-K、阈值全部外置。
6. **文档同步**：README 记录启动与测试命令，开发记录记录每次缺陷闭环。

### 2.8.5 兼容性

# 第三部分 MVP 方案

## 3.1 MVP 定义

**MVP 不是"功能少一点的产品"，而是"用最小成本回答一个关键假设"的 experiment。**

本项目要验证的假设：

> H1：一线维修人员愿意用自然语言描述故障，并接受"系统给方向、人来判断"的协作方式。
> H2：在十几条结构化案例的规模下，检索 + 依据作答已能覆盖高频问题的主要排查路径。
> H3："无依据时明确拒答"不会显著降低信任，反而提升可信度。

**MVP 目标**：在 5 小时 / 2 人日内，交付一个能**当着评审面跑通**的闭环，用于收集 H1~H3 的初步证据。

## 3.2 核心用户与场景

| 要素 | 内容 |
|---|---|
| 主角色 | 设备维修工（3 年以下经验，熟悉设备但缺乏案例积累） |
| 使用时机 | 现场发现异常、尚未停机检修的 5 分钟内 |
| 核心场景 1 | "液压站压力上不去"——需要立刻知道先查什么、有没有安全风险 |
| 核心场景 2 | "空压机高温报警"——需要区分是散热问题还是油路问题 |
| 核心场景 3 | "注塑机模温降不下来"——知识库没这类设备，需要系统诚实说"不知道" |

## 3.3 核心业务闭环

```
描述故障 → 系统检索 → 展示依据 → 给出原因与步骤 → 用户判断是否可执行
                ↑                                        │
                └────────── 未覆盖则明确拒答 ←────────────┘
```

**闭环成立的四条判定**（缺一不可）：

1. 用户输入自然语言即可，无需选择设备树、无需填表单。
2. 系统必须真的去查（有工具调用记录），而不是直接生成。
3. 回答必须带可核对的案例编号，用户能点开看原始案例。
4. 查不到时明确说查不到，并告诉用户补什么信息。

## 3.4 功能范围（MoSCoW）

| 优先级 | 功能 | 说明 | 是否进入 MVP |
|---|---|---|---|
| Must | 自然语言提问 | 多行输入 + 发送 | 是 |
| Must | 本地案例检索 | 24 条案例 / 19 类设备，加权打分 | 是 |
| Must | 工具调用与记录 | 6 个工具（业务 3 + 工程知识 3），界面可查 | 是 |
| Must | 依据作答 | 四段式，带案例编号 | 是 |
| Must | 未覆盖拒答 | 低于阈值即拒答 | 是 |
| Must | 异常处理 | 空输入/缺库/缺密钥/断网 | 是 |
| Must | 一键启动 | 双击即用，无需安装依赖 | 是 |
| Should | 离线兜底 | 无密钥也能演示 | 是（本项目的关键差异化） |
| Should | 知识库浏览 | 侧栏查看全部案例 | 是 |
| Should | 会话导出 | 导出 txt 作为证据 | 是 |
| Could | 在线模型切换 | 设置界面填 Key | 是（成本极低） |
| Could | 多轮上下文 | 保留最近 12 条 | 是 |
| Won't | 真实设备接入 | 需协议栈与现场授权 | 否 |
| Won't | 案例在线编辑 | 需权限与存储设计 | 否 |
| Won't | 语音输入 | 与验证假设无关 | 否 |
| Won't | 用户体系/多租户 | 单机场景无必要 | 否 |

## 3.5 最小功能集合（MVP 五件套）

| 编号 | 功能 | 最小实现 | 验收方式 |
|---|---|---|---|
| M1 | 提问入口 | 一个多行输入框 + 发送按钮 | 输入问题后 1 秒内出现用户气泡 |
| M2 | 检索工具 | `search_fault_cases(query, top_k)` | 输入"液压站压力上不去"，返回 EFA-001，分数 > 0.4 |
| M3 | 依据作答 | 判断/原因/步骤/参考案例 四段 | 回答中出现 `EFA-001` 与至少 3 条处理步骤 |
| M4 | 拒答机制 | 分数低于 0.22 即无命中 | 输入"注塑机模具冷却"输出"暂无案例依据" |
| M5 | 一键启动 | `start.bat` 自动挑解释器 | 干净机器双击 3 秒内出窗口 |

> 这五件事之外的一切（导出、设置、知识库浏览、多轮）都属于"低成本增益"，可以在 10 分钟内补上，但不构成 MVP 成立的必要条件。

## 3.6 优先级排序与理由

| 排序 | 功能 | 用户价值 | 实现成本 | 验证价值 | 决策 |
|---|---|---|---|---|---|
| 1 | 检索 + 依据作答 | 高 | 低 | 直接验证 H2 | 先做 |
| 2 | 工具调用记录 | 中 | 低 | 证明"不是纯生成"，评审硬要求 | 先做 |
| 3 | 未覆盖拒答 | 高 | 低 | 验证 H3（信任度） | 先做 |
| 4 | 一键启动 | 高 | 中（环境适配） | 决定能否交付 | 先做 |
| 5 | 离线兜底 | 中 | 中 | 保证演示不中断 | 次做 |
| 6 | 界面美化/知识库浏览 | 低 | 中 | 间接影响 H1 | 后做 |
| 7 | 多轮上下文 | 中 | 低 | 影响真实使用 | 后做 |
| 8 | 工单导出/设备接入 | 高 | 高 | 与当前假设无关 | 不做 |

**排序原则**：先做"能证伪假设"的功能，再做"让假设更容易被接受"的功能。界面美化排在检索之后，是因为界面再漂亮，答非所问也不会有人用。

## 3.7 明确排除项（防蔓延清单）

1. 不接真实设备、不做协议解析、不下发控制指令。
2. 不做用户注册登录与权限（单机即单用户）。
3. 不做云端同步与多人协同编辑知识库。
4. 不做语音/图片识别输入。
5. 不做自动工单流转与绩效考核。
6. 不做模型微调，只做提示词与检索优化。

> 任何一条被要求加入时，先回答："不加它，本次要验证的假设还能不能验证？" 若答案是"能"，则拒绝。

## 3.8 验证指标

### 3.8.1 北极星指标

**有依据解决率** = （回答中给出了案例编号且用户判定"方向正确"的次数） / 总提问次数。

目标：在 24 条案例覆盖的 19 类设备上 ≥ 70%。

### 3.8.2 指标体系

| 类别 | 指标 | 定义 | 目标值 | 采集方式 |
|---|---|---|---|---|
| 效果 | 有依据解决率 | 见上 | ≥ 70% | 人工标注 + 回答中的编号 |
| 效果 | 无依据率 | 返回"暂无案例依据"的比例 | ≤ 30%（覆盖范围内） | 日志 `hit_count=0` |
| 效果 | 引用准确率 | 引用的案例编号确实与问题相关 | ≥ 90% | 人工抽检 20 条 |
| 效率 | 单轮响应时间 | 从点击发送到出现回答 | 离线 ≤ 50 ms，在线 ≤ 5 s | 界面 meta 与日志 `elapsed_ms` |
| 效率 | 首次可用时间 | 从双击到可提问 | ≤ 3 s | 秒表/自检 |
| 体验 | 降级触发率 | `llm_failed` 占比 | ≤ 10% | 日志 |
| 质量 | 自动化测试通过率 | 测试通过数/总数 | 100% | `run_tests.py` |
| 质量 | 工具调用成功率 | `ok=true` 比例 | ≥ 98% | 日志 `tool_call.ok` |
| 采纳 | 建议可执行率 | 用户认为"步骤能照着做"的比例 | ≥ 80% | 5 人试用问卷 |
| 安全 | 越界输出次数 | 出现设备控制指令或编造案例的次数 | 0 | 人工审查 |

### 3.8.3 指标与假设的映射

| 假设 | 观测指标 | 判定 |
|---|---|---|
| H1 愿意自然语言描述 | 试用者首次输入字数 ≥ 15、无需引导即可提问 | 5 人中 ≥ 4 人 |
| H2 小规模案例够用 | 有依据解决率 ≥ 70% | 达标即成立 |
| H3 拒答不损害信任 | 遇到拒答后仍愿意继续使用的人数比例 ≥ 60% | 达标即成立 |

## 3.9 验证实验设计

| 实验 | 输入 | 期望观察 | 判定标准 |
|---|---|---|---|
| E1 正常问题 | "液压站压力上不去，油缸动作很慢" | 命中 EFA-001，给出 4 条原因 + 6 条步骤，工具记录 2 次 | 回答含 EFA-001 且步骤可执行 |
| E2 未覆盖问题 | "数控冲床送料机构卡料" | 明确"暂无案例依据"，列出已覆盖设备类型 | 不出现任何编造编号 |
| E3 异常输入 | 空字符串 / 断网 / 清空密钥 | 友好提示；断网自动降级；无密钥标注离线模式 | 程序不崩溃，提示可理解 |
| E4 交叉验证 | "风机振动大，轴承温度高" | 命中 EFA-012，且不被 EFA-002（主轴异响）抢占 | Top1 正确 |
| E5 边界参数 | `top_k=99` / 未知 `case_id` | Top-K 收敛到 5；返回"案例编号不存在" | 无异常栈 |

**实验执行方式**：5 名维修/设备相关背景人员，每人 3 个真实问题，观察首次输入耗时、是否追问、是否采纳建议；同步记录日志指标。样本量小，只做方向性判断，不做显著性结论。

## 3.10 MVP 交付节奏

| 阶段 | 时长 | 交付 |
|---|---|---|
| Day 1 上午 | 2 h | 需求收敛 + 12 条案例 + 检索可用（`--cli` 能回答） |
| Day 1 下午 | 3 h | 工具层 + 编排层 + 桌面界面 + 5 条核心用例自测 |
| Day 2 上午 | 2 h | 异常处理 + 测试补齐 + 一键启动适配 |
| Day 2 下午 | 1 h | 试用与指标采集、演示彩排、文档归档 |

**范围守则**：任何一个功能超出 30 分钟仍未完成，立即降级为 Could 或移出 MVP。

## 3.11 MVP 退出条件

| 结论 | 判定条件 | 下一步 |
|---|---|---|
| 继续投入 | 有依据解决率 ≥ 70%，5 人中 ≥ 4 人愿意继续用 | 进入 P1：扩案例库、加同义词、SQLite 化 |
| 需要调整 | 有依据率 < 70% 但拒答被接受 | 优化检索（扩关键词、调权重），不扩功能 |
| 方向存疑 | 用户更希望"直接给结论"而非"给依据" | 重新设计交互：结论优先 + 折叠依据 |
| 停止 | 用户认为"查手册更快" | 停止投入，转为内部知识库检索工具 |

| JSONL | 每行一个 JSON 对象的日志格式，便于追加与逐条解析 |
| Dice 系数 | 两个集合相似度度量，本文用于中文二元组文本相似度计算 |

## 附录 C 项目知识库体系（v2.0）

### C.1 定位

案例库回答"设备怎么修"，项目知识库回答"这个项目怎么用、怎么改"。两者字段不同、检索权重不同，因此独立成库：

| 维度 | 案例库 `data/fault_cases.json` | 项目知识库 `data/project_kb.json` |
|---|---|---|
| 服务对象 | 设备维修工 | 开发与维护人员（含 AI 编码助手） |
| 条目数 | 12 条案例 | 69 条知识，11 个分类 |
| 关键字段 | 现象/原因/步骤/风险 | 背景/调用条件/参数规范/实操步骤/排障/最佳实践/关联条目/适用范围/版本约束 |
| 检索信号 | 设备名 + 关键词 + 现象相似度 | 符号命中 + 标签 + 标题/正文相似度 |
| 默认阈值 | 0.22 | 0.18 |

### C.2 分类体系

| 分类 | 条数 | 覆盖内容 |
|---|---|---|
| guide | 7 | 上手路线、术语表、排障索引、FAQ、维护流程、版本策略、检索权重 |
| architecture | 4 | 分层与依赖方向、双模式、扩展点、线程模型 |
| module | 10 | 每个源码文件的职责与边界（含校验模块） |
| api | 14 | 类与方法级签名、参数、返回、调用条件（含路由、统计） |
| tool | 6 | 6 个工具的契约与适用场景 |
| data | 5 | 领域模型、案例字段与知识库元信息 |
| config | 3 | Settings 字段、配置优先级、检索调参 |
| error | 5 | 统一返回约定、错误标识、降级策略、错误文案、校验错误码 |
| dependency | 5 | 标准库清单、零依赖约束、工具链、exe 打包、双远程发布 |
| convention | 6 | 目录命名、日志格式、测试规范、审查清单、提交规范、文档构建 |
| boundary | 4 | 安全边界、版本兼容、已知限制、性能容量 |

### C.3 条目字段规范

共 22 个字段，分六个维度：

| 维度 | 字段 | 说明 |
|---|---|---|
| 定位 | `summary` / `background` / `when_to_use` | 一句话结论、设计动机、调用条件 |
| 契约 | `symbol` / `signature` / `inputs` / `outputs` | 源码符号、签名、参数规范、输出格式 |
| 操作 | `steps` / `scenarios` | 实操步骤（2~6 条，按顺序）、使用场景 |
| 风险 | `cautions` / `troubleshooting` | 禁止做法、排障三元组（现象/检查/处理） |
| 经验 | `best_practices` | 正向做法，与注意事项互补 |
| 边界 | `related` / `scope` / `version` / `aliases` / `tags` / `refs` | 交叉引用、适用范围、起始版本、同义词、标签、出处 |

### C.4 工具扩展

新增 3 个工具，与原有 3 个业务工具并列注册：

| 工具 | 用途 | 关键参数 |
|---|---|---|
| `search_project_kb` | 检索工程知识（可按分类过滤） | `query`、`category`、`top_k` |
| `get_kb_entry` | 按编号读取完整条目 | `entry_id` |
| `list_kb_categories` | 列出分类与条目数 | 无 |

工具是否注册取决于是否注入 `ProjectKB`：未注入时 `specs()` 只返回 3 个业务工具，便于单独测试与裁剪。

### C.5 离线选路

无模型时由 `Agent.route()` 做关键词打分：工程词（模块/接口/配置/依赖/项目/部署…）与故障词（故障/报警/温度/压力/设备…）分别计分，工程分严格大于故障分才走项目知识库，否则走案例库。八条正反例已固化为测试，避免"答非所问"。

### C.6 一致性保障

`python tools/verify_kb.py` 校验九个维度：字段齐全、ID 唯一、分类无孤儿、引用文件存在、符号存在、签名参数一致、数据类字段一致、工具契约双向对齐、正文数字断言不过期。任何不一致都会使命令非 0 退出，并使 `tests/test_project_kb.py` 失败；另有两条例行测试会故意篡改副本，验证校验器本身有效。
