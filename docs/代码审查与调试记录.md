# 三、Agent 调用工具的关键函数

调用链（离线模式，也是课堂演示的默认路径）：

```
app.py --cli
  └─ Agent.ask()                     agent.py:129   入口：空输入/知识库缺失/在线与离线分流
       ├─ Agent.route()              agent.py:107   工程问题 or 设备故障（决定走哪套知识库）
       ├─ Agent._ask_offline()       agent.py:238   规则引擎：先检索、再取详情、最后套模板
       │    └─ ToolRegistry.execute()  tools.py:221  ★ 所有工具调用的唯一入口
       │         ├─ _normalize_arguments()  tools.py:266  参数清洗（本次修复点）
       │         ├─ _search_fault_cases()   tools.py:288  → KnowledgeBase.search()
       │         ├─ _get_case_detail()      tools.py:309  → KnowledgeBase.get()
       │         └─ _summarize()            tools.py:376  生成可读摘要供界面/日志展示
       └─ Agent._ask_llm()           agent.py       在线：function calling 循环（最多 6 轮）
```

关键点：**在线与离线共用同一个 `ToolRegistry.execute()`**，区别只在"谁决定调用"。因此参数清洗、异常兜底、调用记录都只需在一处保证，这也是我把修复点选在这里的原因。

`execute()` 的职责边界很清楚：参数归一化 → 找实现 → 执行 → 异常转结构化结果 → 记耗时与摘要。它返回 `(result, ToolCallRecord)`，界面右侧"工具调用"表格直接渲染这个记录。

# 六、修复：模型多传一个参数就让工具整体失败

## 6.1 现象

代码审查时怀疑参数透传过严，于是用探针脚本逐个试（这也是"检查工具调用结果"的一部分）：

| 调用 | 修复前结果 |
| --- | --- |
| `search_fault_cases({"query": "液压站压力上不去"})` | ok=True，命中 1 条 |
| `search_fault_cases({"query": "...", "reason": "先检索"})` | **ok=False，`参数不合法：got an unexpected keyword argument 'reason'`** |
| `search_fault_cases({"q": "液压站压力上不去"})` | **ok=False，同上（键名不匹配）** |
| `get_case_detail({"case": "efa-001"})` | ok=True（`KnowledgeBase.get` 内部做了大小写归一） |

## 6.2 根因

`ToolRegistry.execute()` 原来直接 `fn(**arguments)`，把模型返回的 JSON 参数原样展开到函数签名上。模型多带一个自解释字段（`reason`、`explanation`）或用同义键名（`q`、`limit`）时，Python 抛 `TypeError`，被 `except TypeError` 转成"参数不合法"，**整次调用判失败**。

对诊断类 Agent 来说这不只是"少查一次"，而是**主动放弃证据**：检索失败后模型只能凭记忆作答，恰恰是本项目最想避免的行为。

## 6.3 修复

在 `execute()` 与具体实现之间加一层参数清洗，按函数签名决定"留、改名、丢"：

| 处理 | 规则 | 例子 |
| --- | --- | --- |
| 保留 | 键名在函数签名内 | `query`、`top_k`、`case_id` |
| 改名 | 命中同义表 `ARG_ALIASES` 后落回真实参数名 | `q→query`、`limit→top_k`、`case→case_id` |
| 丢弃 | 既不在签名也不在同义表 | `reason`、`explanation` |

丢弃不是静默丢弃：被丢的键会写回工具结果 `ignored_arguments`，模型下一轮能看到自己多传了什么并可自行纠正；`ToolCallRecord.arguments` 记录的是**实际执行的参数**，日志与代码对得上。

新增 `_normalize_arguments()`（`tools.py:266`），`execute()` 里改为：

```python
arguments, ignored = self._normalize_arguments(fn, arguments)
result = fn(**arguments)
if ignored:
    result = {**result, "ignored_arguments": ignored}
```

## 6.4 验证

| 调用 | 修复后 |
| --- | --- |
| 带 `reason` | ok=True，命中 1 条，`ignored_arguments=['reason']` |
| 用 `q` | ok=True，`result["query"]` 正确回填 |
| 用 `limit` | ok=True，按 2 条返回 |
| 只给 `reason`（漏了 query） | 仍然 ok=False，`检索关键词为空` —— 清洗只丢多余键，不放过缺参 |

新增 3 条单元测试锁定行为（`tests/test_tools.py`）：多余参数不失败、同义名被映射、缺参仍报错。

# 八、后续建议

1. **把断点调试补进 IDE**：本机 VS Code 装了 Python 扩展后，加 `.vscode/launch.json`（`"module": "app"`, `"args": ["--cli", "液压站压力上不去"]`）即可直接在 `execute()` 上按 F5，交互体验优于 pdb 脚本。
2. **`ignored_arguments` 可升级为软告警**：若某一轮工具调用被丢弃的参数超过 2 个，可在系统提示里回灌一句"参数名不符合工具契约"，比让模型自己发现更稳。
3. **补一个参数契约测试**：把 `specs()` 里的 JSON Schema 与函数签名做自动比对，避免以后改签名忘了改声明（当前这类一致性由人工保证）。
