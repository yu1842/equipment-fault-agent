> 本文按时间顺序记录"需求 → 方案 → 编码 → 调试 → 测试 → 交付"过程中真实发生的问题，

## 一、需求拆解与方案决策

| 决策点 | 备选方案 | 最终选择 | 理由 |
|---|---|---|---|
| 客户端形态 | Web 页面 / WinForms / Tkinter | **Tkinter** | Python 标准库自带，零安装、单进程、可直接打包，符合"无需复杂依赖即可启动" |
| 模型调用 | openai SDK / requests / urllib | **urllib** | 避免任何第三方包，`uv sync` 后无需下载依赖 |
| 检索方案 | 向量库 / jieba 分词 / 规则加权 | **规则加权 + 二元组相似度** | 12 条案例规模下，向量库属于过度设计；纯标准库即可达到可解释的排序结果 |
| 无密钥时的行为 | 直接报错 / 返回固定文本 / 规则兜底 | **规则兜底 + 显式标注模式** | 课堂上没有密钥也必须能演示完整闭环，但不能把固定文本伪装成模型输出 |

**安全边界确认**：只读 `data/fault_cases.json`；不引入 `socket` 对设备的连接；
不生成任何设备控制指令。`llm.py` 是唯一的外网出口，且可被"强制离线"开关关闭。

## 二、编码阶段的真实问题

### 问题 1：Agent 模块导入即报语法错误

- **现象**：`python app.py --list` 抛出 `SyntaxError: invalid syntax`，定位到 `tools.py` 的
  `execute` 方法。
- **原因**：函数签名写成了两行，且第一行末尾漏了冒号：

  ```python
  def execute(self, name: str, arguments: dict | str)
  -> tuple[dict, ToolCallRecord]:
  ```

- **修复**：合并为单行签名。
- **验证**：

  ```
  $ python app.py --list
  知识库：...\data\fault_cases.json
  版本：1.0.0  条数：12
  ```

### 问题 2：工具返回结构不统一，Agent 循环难以消费

- **现象**：初版各工具直接返回字符串或抛异常，模型侧拿不到稳定结构。
- **修复**：统一约定 `{"ok": bool, ...}`；`ToolRegistry.execute()` 内部把
  `ToolError` / `TypeError` / 其他异常统一转成 `{"ok": false, "error": "..."}`，
  并同时产出 `ToolCallRecord`（工具名、参数、耗时、摘要），供界面与日志使用。
- **验证**：`tests/test_tools.py` 覆盖"未知工具""案例不存在""参数非法 JSON""空查询"四种失败路径。

### 问题 3：模型返回空回答导致界面一直等待

- **现象**：在线模式下偶发模型只返回 `tool_calls` 不返回正文，循环结束后无内容可展示。
- **修复**：`_ask_llm` 每轮检查 —— 有 `tool_calls` 继续，有正文返回，
  否则抛 `LLMError("模型返回了空回答")`；外层捕获后自动降级到离线模式，界面不会卡死。
- **验证**：`tests/test_agent.py::TestAgentOnlineFallback` 用不可达地址模拟，确认降级成功且
  回答中仍包含 `EFA-012` 的完整建议。

## 三、界面调试阶段的真实问题

### 问题 4：关闭窗口后 Tk 报 `invalid command name`

- **现象**：测试套件全部通过，但结束时输出

  ```
  invalid command name "2173363156736_drain_queue"
      while executing "2173363156736_drain_queue" ("after" script)
  ```

- **定位**：`_drain_queue` 用 `after(120, ...)` 自循环；`destroy()` 之后该回调仍会触发一次。
- **修复**：保存 `self._poll_id`，重写 `destroy()`：

  ```python
  def destroy(self):
      self._alive = False
      if self._poll_id is not None:
          try: self.after_cancel(self._poll_id)
          except tk.TclError: pass
          self._poll_id = None
      super().destroy()
  ```

- **验证**：`python run_tests.py` 输出不再有噪声，`Ran 30 tests ... OK`。

### 问题 5：界面测试断言 `chat.winfo_width()` 为 1

- **现象**：`test_layout_has_positive_size` 失败，对话区宽度为 1。
- **定位**：`update_idletasks()` 只处理挂起的布局请求，不驱动窗口映射（map）与几何计算。
- **修复**：测试中改为 `update_idletasks()` + `update()`。
- **验证**（实测输出）：

  ```
  窗口: 1180 x 760  mapped=1
  对话区: 589 x 492
  输入框高度: 73
  ```

### 问题 6：默认 `python` 缺少 Tkinter，双击即失败

- **现象**：`python app.py` 报 `ModuleNotFoundError: No module named 'tkinter'`（该解释器为精简版）。
- **定位**：`where python` 命中多个解释器，其中一个不含 tcl/tk。
- **修复**：`start.bat` 遍历 `py -3.15 / py -3.14 / py -3.13 / py -3 / python`，
  用 `-c "import tkinter"` 逐个探测，命中后取同目录 `pythonw.exe` 启动，避免黑框。
- **验证**：双击 `start.bat` 正常弹出窗口；`start.bat selftest` 输出 6 项检查全部 True。

## 四、检索质量调优

初版仅用关键词命中，出现两个问题：

1. **漏召回**：用户说"油缸没劲、压力表上不去"，未命中"压力不足"关键词；
2. **误召回**：查询"报警"命中多条案例，排序不稳定。

改进后的打分（`knowledge.py`）：

```
score = 0.42 * 设备名命中
      + 0.20 * 关键词命中数(上限 4 个)
      + 0.55 * 现象文本 Dice 相似度
      + 0.20 * 全案例文本 Dice 相似度
score = 1 - exp(-1.15 * score)      # 压缩到 0~1，避免线性叠加越界
```

实测：`液压站压力上不去，油缸动作无力` → EFA-001，score = 0.701；
`注塑机模具冷却水路堵塞` → 无命中（低于阈值 0.22），走"缺乏依据"分支。
两个用例已固化为单元测试，防止后续调参回退。

## 八、v1.1 迭代：项目知识库扩展

**目标**：让 Agent 除了"设备怎么修"，还能回答"这个项目怎么用、怎么改"，并保证答案与源码一致。

### 8.1 设计决策

| 决策点 | 备选 | 选择 | 理由 |
|---|---|---|---|
| 知识库形态 | 复用 fault_cases.json / 新文件 | **新文件 `data/project_kb.json`** | 两类知识字段不同（工程知识有 signature/scope/version），混在一起会让检索串味 |
| 检索实现 | 复用 KnowledgeBase | **独立 `ProjectKB`** | 工程问题靠符号命中，权重要单独调；共用类会导致调参互相干扰 |
| 新增配置项 | 加 `project_kb_path` | **不加**，由 `kb_path` 父目录推断 | 少一个字段就少一处配置漂移，Settings 仍是 10 个字段 |
| 离线选路 | 一律走故障库 / 关键词路由 | **`Agent.route()` 打分路由** | 无密钥时也必须能正确回答工程问题，不能答非所问 |
| 一致性保障 | 人工核对 | **`kbcheck.py` + AST 比对 + 测试锁定** | 文档漂移是知识库类项目最大的隐性债务 |

### 8.2 遇到的问题

**问题 7：离线模式把工程问题当成设备故障**

- 现象：问"这个项目支持分布式部署吗？集群怎么配？"，返回的是"本地知识库暂无该故障的案例依据"。
- 定位：`PROJECT_HINTS` 里没有"项目/部署"等词；且路由规则用了 `>=`，平局时偏向工程分支，实际这里工程分为 0。
- 修复：补充"项目/部署/服务化/多用户/数据库/版本/单元测试/文档"等词；判定改为 `project_score > fault_score` 才走工程分支（主场景仍是设备咨询）。
- 验证：8 条正反例固化为 `TestAgentRouting`，其中"设备异常振动"必须判为 fault。

**问题 8：一致性校验初次运行误报 12 个错误**

- 现象：`verify_kb.py` 报 `BAD_SYMBOL: main 不存在`、6 个 `BAD_SYMBOL: search_fault_cases…`、5 个 `BAD_SIGNATURE: FaultCase 参数不一致`。
- 定位：① 工具名是注册表键而非 Python 符号；② 数据类条目的括号里写的是字段，不是函数参数；③ `main` 在根目录 `app.py`，而索引只扫了 `src/efa`。
- 修复：工具条目跳过符号检查（改由工具契约校验负责）；类条目比对 `AnnAssign` 字段集合；索引补充 `app.py`。
- 验证：`0 错误 0 警告`；同时新增两条"反向测试"——故意篡改副本的参数名/符号，校验器必须报 `BAD_SIGNATURE` / `BAD_SYMBOL`。

**问题 9：`tools.py` 里写了会截断字符串的中文引号**

- 现象：新增工具后导入即 `SyntaxError`。
- 定位：提示文案 `说明"未收录"，不要臆造` 使用了 ASCII 双引号，提前结束字符串。
- 修复：改用「未收录」式表述；`python -m compileall src` 作为提交前检查。

## 九、v2.0 迭代：知识库内容体系化

**目标**：把 v1.1 的"目录式知识库"升级成"可实操的知识库"——每条都能回答"为什么、怎么做、出问题怎么办"。

### 9.1 先审计再动笔

用脚本统计了 52 条条目的字段覆盖率与符号覆盖：

| 审计项 | 结果 | 结论 |
|---|---|---|
| 字段覆盖 | 无 background/steps/troubleshooting/best_practices/related | 条目只能"读"不能"用" |
| 符号覆盖 | 180 个公开符号中仅 29 个有条目 | kbcheck、Agent.route 等核心机制缺失 |
| 主题覆盖 | 无上手/术语/排障/FAQ/打包/审查/容量 | 使用与运维环节全靠口口相传 |
| 粒度 | 39 条无 inputs、27 条无 signature | API 类与非 API 类信息量差距过大 |

### 9.2 设计决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 字段扩展方式 | 在 v1 schema 上增补 6 个字段，而非另建"实践库" | 同一主题拆两处会让检索与维护都翻倍 |
| 新增分类 | 新建 guide（导航与速查）并排在最前 | 新人第一需求是"从哪看起"，不是"某函数签名" |
| 交叉引用 | 强制双向闭合，迁移脚本自动回填反向边 | 单向引用会让导航走进死胡同 |
| 内容来源 | 一次性迁移脚本 + JSON 为唯一数据源 | 52 条手写 JSON 易出错，脚本可校验可重复 |
| 质量守门 | 把"粒度/占位词/悬空引用"也做成校验项 | 只校验代码一致性，挡不住内容退化 |

### 9.3 遇到的问题

**问题 10：中文内容里的 ASCII 双引号会截断字符串**

- 现象：数据模块 `python -m py_compile` 报 `SyntaxError`，指向中文句子中间。
- 定位：文案里写了 `说明"未收录"` 这类 ASCII 引号，提前结束了 Python 字符串。
- 修复：统一改用「」，并把数据拆成 4 个纯数据模块，每写完一个立刻 `ast.parse` 校验。

**问题 11：新校验规则一上线就误报 6 条占位词**

- 现象：`KB-GUIDE-006` 报含「略」、`KB-ARCH-003` 报含「xxx」。
- 定位：「策略」「忽略」里的略被当成占位词；`KB-xxx` 是正常的编号示例写法。
- 修复：占位词改为 `TODO:`/`待补充`/`待完善`/`示例文本`/`暂无内容`/`占位符`/`TBD`，避免误伤自然语言。

**问题 12：KB-DATA-006 的字段清单没跟着 KBEntry 一起改**

- 现象：校验报 `BAD_FIELDS`，文档列 16 个字段、实际 22 个。
- 定位：给 KBEntry 加了 6 个字段，却没更新数据结构条目里的签名。
- 修复：把 signature 写成完整 22 个字段并重新校验；这条正是校验器存在意义的实证。

**问题 13：粒度阈值一开始定得过严**

- 现象：4 条警告（related 9 条超上限、tags 2 条低于下限、2 条标题超长）。
- 处理：related 上限放宽到 10（枢纽条目天然多引用）、tags 下限保持 3 并补齐数据、两条标题改写。

## 十、v2.1 迭代：知识库维护与索引同步

**目标**：把 v2.0 的内容做一次"体检 + 清淤 + 补新"，并让检索从"每次全量扫描"变成"有索引可查"。

### 10.1 维护前审计（先量化再动手）

| 审计项 | 维护前 | 结论 |
|---|---|---|
| 高相似条目对（标题+摘要 Dice > 0.30） | 15 对，最高 0.51 | 存在同主题双份描述，检索时互相抢占 |
| 过时数字 | 3 处（59 项测试、10 个分类、版本线缺 v2.0 之后变化） | 内容与实现脱节 |
| 检索不到自己（用标题检索非 Top1） | 3 / 65 | 条目存在但用户搜不到，等于没有 |
| 未文档化的新能力 | `ProjectKB.stats`、`related_entries`、索引机制 | 代码先行、文档缺位 |

### 10.2 维护动作

| 动作 | 数量 | 代表 |
|---|---|---|
| 新增 | 6 | 统计接口、元信息、校验错误码、文档构建、双远程发布、检索权重 |
| 修改 | 13 | 修正过时数字 3 处、合并被删条目内容 2 处、补别名声明的 4 处、收窄重复定位 4 处 |
| 删除 | 2 | `KB-DATA-002`（SearchHit）并入 `KB-API-003`；`KB-DATA-005`（文件结构）并入 `KB-DATA-001` |

删除不是"删掉就完事"：脚本会清理所有指向被删条目的 `related`，再重新做双向闭合，避免导航断链。

### 10.3 索引同步

问题：检索是线性扫描，69 条虽快，但"数据改了索引没跟上"这类隐患无法表达。

方案：

1. `src/efa/kb_index.py` 生成倒排索引（词项 → 条目编号），写入 `data/kb_index.json`，同时记录源数据 sha256；
2. `ProjectKB` 加载时比对哈希，一致才启用倒排候选集，否则标记 `stale` / `missing` 并退回线性扫描；
3. `verify_kb.py` 新增 `INDEX_MISSING` / `INDEX_STALE` 检查；
4. `tools/rebuild_index.py` 提供重建与 `--check`。

代价与收益：2070 个索引词、69 条数据，重建耗时不足 1 秒；索引与数据不一致时不会给出错误结果，只是失去加速，属于安全降级。

### 10.4 新增的硬校验：可检索性

`verify_kb.py` 增加第 10 类校验——**用条目自己的标题检索，Top1 必须是自己**，否则判 E 级错误。

- 维护前 65 条中有 3 条不达标（两条 API 被各自的模块条目抢占、一条数据结构被字段条目抢占）；
- 处理方式不是调权重，而是补 `aliases` 与 `tags`，让"专有名词"能唯一定位；

### 10.6 遇到的问题

**问题 14：合并内容后反而制造了新的重复**

- 现象：把"配置优先级"并入 `KB-API-008` 后，它与 `KB-CFG-002` 的相似度升到 0.43。
- 定位：接口条目本该只讲"怎么读写"，规则条目讲"优先级怎么定"，两者混写必然重复。
- 修复：`KB-API-008` 回归接口定位，优先级细节只保留一句"完整规则见 KB-CFG-002"。

**问题 15：给条目补了别名，检索归属仍不对**

- 现象：`KB-API-010` 补了 `SessionLog` 别名后，用标题检索仍被 `KB-MOD-006` 抢占。
- 定位：模块条目的 `tags` 里也有"会话日志"，标签命中 0.18 叠加后超过别名。
- 修复：给 API 条目补更具体的别名（写日志方法、日志落盘）并调 tags，同时接受"模块条目在泛化查询上占优"这一合理分层。

**问题 16：索引写入时机没定，导致短暂 stale**

- 现象：改完数据直接跑测试，`test_index_is_fresh` 失败。

## 十二、自检闭环记录（v2.2.1）：三例"生成 → 自检 → 调整 → 验证"

这一章不是功能开发，而是把开发过程中真实发生过的三次自检固化成可复现记录，交付件为 `docs/AI代码生成自检记录.md`（Word 版同名）。

### 12.1 为什么要单独记录

功能记录说明"做成了什么"，自检记录说明"怎么知道自己做对了"。前者的证据是需求，后者的证据必须是机器输出：测试结果、编译报错、检索命中率、界面截图、提交差异。缺了这些，过程就只能靠复述。
