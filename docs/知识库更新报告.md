## 一、审计发现：v1.1 到底缺什么

在动手补内容前，先用脚本做了一次全量体检，结论如下。

### 1.1 结构缺口

| 缺失维度 | 表现 | 影响 |
|---|---|---|
| 背景说明 | 只有结论，没有「为什么这样设计」 | 读者知其然不知其所以然，改动时容易推翻关键约束 |
| 实操步骤 | 只有字段说明，没有「具体怎么做」 | 条目可读不可用，遇到问题仍要翻代码 |
| 排障方案 | 完全没有 | 出问题时知识库帮不上忙，退化成参考手册 |
| 最佳实践 | 只有注意事项（禁止项），没有正向做法 | 只知道不能做什么，不知道应该做什么 |
| 交叉引用 | `related` 字段不存在 | 条目之间是孤岛，无法从 A 导航到 B |
| 检索别名 | 只有 tags | 用户说「怎么加功能」搜不到「工具插件式扩展点」 |

### 1.2 主题缺口

审计对比了 180 个公开符号与 52 条条目，发现三类空白：

1. **代码有、知识库无**：`kbcheck.py`（一致性校验）、`Agent.route()`（离线路由）完全没条目，而它们恰恰是 v1.1 新增的核心机制。
2. **使用有、文档无**：没有上手路线、术语表、排障索引、FAQ —— 新人拿到项目不知道从哪看起。
3. **运维有、规范无**：打包 exe、代码审查、提交规范、性能容量边界，都只在口头或提交信息里，没有沉淀。

### 1.3 粒度不均

`summary` 中位 44 字尚可，但 39/52 条没有 `inputs`、27/52 条没有 `signature`，导致 API 类与非 API 类条目在信息量上差距过大，Agent 检索后拿到的内容质量不稳定。

| `related`（交叉引用） | 52 | 共 **242** 条双向关联 |

字段覆盖率（脚本实测）：`background`、`when_to_use`、`steps`、`troubleshooting`、`best_practices`、`related`、`aliases` **均为 100%**。

### 3.2 富化前后对比（以 KB-ARCH-003 工具扩展点为例）

**v1.1（问题）**：只有一句结论「新增工具只改 tools.py 两处」，读者仍不知道具体改哪、改错了会怎样、模型不调用怎么办。

**v2.0（可用）**：

| 维度 | 内容 |
|---|---|
| 背景 | 工具会持续增加，若每个都改 agent，编排层会退化成 if-else 迷宫 |
| 步骤 | 登记 `_impl` → 补 `specs()` 声明 → 实现并统一返回 → 可选补摘要与提示词 |
| 排障 | 模型不调用（查描述）／参数不合法（查 required） |
| 最佳实践 | 工具只读、不在 agent 里写工具名分支 |
| 关联 | KB-MOD-003、KB-API-006、KB-API-007 三条双向可达 |

## 四、交叉引用与检索优化

### 4.1 引用网络

- 关联边 **242 条**，平均 **3.72 条/节点**，无自引用、无悬空编号。
- 引用强制**双向闭合**：A 引用 B 时自动为 B 回填 A，保证从任意入口都能走到相邻节点。
- `get_kb_entry` 现在额外返回 `related` 列表（编号 + 标题 + 分类），Agent 可据此继续导航，不必二次检索。

引用最密集的枢纽节点：`KB-DATA-001`（案例字段，9 条关联）、`KB-MOD-002`（检索模块）、`KB-ARCH-001`（分层架构），符合「改数据、改检索、改分层」这三类高频改动。

### 4.2 检索逻辑改进

| 改进 | 说明 | 效果 |
|---|---|---|
| 别名加权 | `aliases` 命中每项 +0.26，最多取 2 项 | 用户口语「怎么加功能」可命中 KB-ARCH-003 |
| 背景入相似度 | 正文相似度计算纳入 `background` | 语义覆盖更广，短查询也能命中 |
| 结果带 related | 检索结果附 4 条关联编号 | 一次检索即可扩展阅读路径 |
| 分类导航 | `list_kb_categories` 返回 11 类及条目数 | 先缩范围再检索，减少无效查询 |

### 4.3 导航结构

guide 作为入口层，向下引出六条路径：

1. 快速上手 → architecture → module → api（新人主线）
2. 术语表 → 全库用词基准（横向约束）
3. 排障索引 → error / boundary / module（问题驱动）
4. FAQ → boundary / architecture（评估驱动）
5. 维护流程 → module（kbcheck）/ data（运营驱动）
6. 版本策略 → convention / dependency（发布驱动）

新增的 guide 分类刻意放在分类排序最前，使其成为检索与浏览的默认入口。

## 五、标准化与校验

### 5.1 字段规范（写入 schema 元信息）

| 字段 | 规范 |
|---|---|
| `id` | `KB-<分类缩写>-<三位序号>`，前缀必须与分类一致 |
| `summary` | 一句话结论，12~90 字 |
| `aliases` | 2~6 个同义说法 |
| `background` | 说明动机，不少于 12 字 |
| `steps` | 2~6 条，按执行顺序 |
| `troubleshooting` | 每项含 `symptom` / `check` / `fix`，三者均不可为空 |
| `best_practices` | 2~5 条正向做法 |
| `related` | 2~10 条，必须双向闭合、不得自引用 |
| `version` | `>=x.y.z` 形式，表示起始适用版本 |
| `tags` | 3~8 个 |

### 5.2 校验维度（9 类，其中 3 类为本次新增）

| # | 维度 | 级别 | 说明 |
|---|---|---|---|
| 1 | 字段齐全 | E | 20 个必填字段均存在 |
| 2 | ID 唯一 + 前缀一致 | E | 重复编号、前缀与分类错配 |
| 3 | 分类存在 | E | 条目分类必须在 categories 中 |
| 4 | 引用文件存在 | E | `refs` 指向的路径必须真实 |
| 5 | 符号存在 | E | 声明的类/方法/字段必须能被 AST 找到 |
| 6 | 签名一致 | E | 括号内参数名与实际函数参数一致 |
| 7 | 工具契约对齐 | E | 工具条目与 `specs()` 双向一致 |
| 8 | **交叉引用完整性** | E/W | 悬空编号（E）、自引用（E）、单向引用（W） |
| 9 | **粒度与占位词** | E/W | 长度区间、条数区间、TODO/待补充等占位词（E） |

新增的第 8、9 类，正是为了让「内容质量」也能被机器守住，而不只是「代码一致性」。

## 七、遗留问题与下一步

| 问题 | 影响 | 计划 |
|---|---|---|
| 私有方法（如 `_ask_llm`）未单独成条 | 调试时缺少细粒度说明 | 视需要并入所属类的条目，不单独开条 |
| 条目仍为线性检索 | 超过 300 条时延迟上升 | 到量后换倒排索引，接口不变 |
| 缺少条目使用频次统计 | 无法判断哪些条目真正有用 | 从 `logs/` 统计 `get_kb_entry` 的 entry_id 分布 |
| 英文条目缺失 | 无法对外分享 | 视需要增加 i18n 字段，不做全量翻译 |
